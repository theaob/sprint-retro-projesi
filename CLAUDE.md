# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev          # Vite (5173) + Express/WS (3000) concurrently — main dev loop
npm run dev:server    # Express/WS server only
npm run dev:client    # Vite dev server only
npm run build         # Production frontend build -> dist/
npm start             # Run the built app (Express serves dist/ + API + WS on :3000)
npm test              # Full test suite (vitest run)
npx vitest run test/auth.test.js   # Single test file
npm run lint           # Biome lint (server/, src/, test/, *.js)
npm run format          # Biome format --write
```

In dev, Vite proxies `/api` and `/s/` to `localhost:3000`, so the frontend always talks to one origin. CI (`.github/workflows/ci.yml`) runs lint → test → build on every push/PR to `main`.

## Architecture

**Two Express entry points.** `server/app.js` builds the Express app (middleware, `/api` routes, `/s/:code` short-link redirect, static `dist/` serving) with no `listen()` call, so it's importable directly in tests via `supertest`. `server/index.js` wraps it with an HTTP server, attaches the `ws` WebSocket server from `server/realtime.js` (`attachRealtime(server)` — rooms, presence, typing relay, payload cap and per-socket rate limit), and is the actual `npm start` entry point. Route handlers call a `broadcast(retroId, payload)` function injected from `index.js` into `routes.js` via `setBroadcast()` — this is how REST mutations (add entry, vote, rename column, finish retro, etc.) fan out to every connected client in that retro's WS room.

**Database migrations are numbered, append-only steps.** `server/db.js` gates schema changes on SQLite's `PRAGMA user_version`: each `if (schemaVersion < N) { ...; db.pragma('user_version = N') }` step runs exactly once per database. Step 1 is the whole pre-versioning history (the original `CREATE TABLE`s plus every old `try { ... } catch { console.error(...) }` migration block, kept verbatim); a database created before versioning reads `user_version` 0 and replays step 1 once. **Never edit or remove an existing step**: to change the schema, append a new step with the next number, even to reverse something an earlier step did (step 1 has several examples of one block undoing an earlier one). Keep each step safe to re-run (`table_info` / `IF NOT EXISTS` guards), since a crash between the change and the version bump replays it. `test/migrations.test.js` checks that a second boot applies nothing.

**Auth is a Bearer session token**, not JWT: `server/auth.js`'s `loadUser` middleware reads `sessions` by token and attaches `req.user` (or `null`) on every request; `requireAuth`/`requireAdmin` gate specific routes, and both also refuse an account still flagged `must_change_password` (the seeded admin/admin) — only routes using `requireAuthAllowPending` (`/auth/me`, logout, changing your own password) let it through. Retro boards themselves are public (no auth required to view/vote) — voting and anonymous participation are scoped by a client-generated `participant_id` (see `getParticipantId()` in `src/utils.js`) rather than a login; the server stores guest votes as `anon:<participant_id>` (see `voterId()` in `routes.js`) so a guest can never act under a real user's id. Finished retros reject new entries and votes server-side. Route input goes through the helpers at the top of `routes.js` (`cleanString`, `optionalString`, `passwordError`, `parseColumnNames`, and the `LIMITS` table of max lengths); public board writes are rate-limited per IP (`boardWriteLimiter`), and `X-Forwarded-For` is trusted only when the `TRUST_PROXY` env var is set (`server/app.js`).

**Staged retros.** A retro created with `staged: true` has `retros.phase` = `setup` → `writing` → `voting` → `discussing` (NULL for a simple retro, which behaves as before); `status` still says active/finished, and finished is the wrap-up. Only the facilitator (owner or admin) changes stage (`PUT /retros/:id/phase`), focus (`/focus`) and timer (`/timer`). Notes can only be added while writing and votes cast while voting. Visibility is enforced on the server in `entryForViewer()` (`routes.js`): while writing, a viewer gets full text only for notes whose `entries.participant_id` matches their `voterId()` — everyone else gets `{ hidden: true, text: '' }`, in GET responses *and* WebSocket broadcasts — and during voting `votes` is `null` (the room only gets `vote:progress` counts). `participant_id` is never sent to clients. Keep any new entry-returning code path going through `entryForViewer()`.

**Frontend is Preact + htm everywhere.** `src/App.js` is the hash router (`#/`, `#/login`, `#/register`, `#/app`, `#/templates`, `#/users`, `#/account`, `#/retro/:id`) with the sign-in/admin/must-change-password guards; `src/main.js` imports the stylesheets and mounts it. Every view is a Preact component written with `htm` tagged templates (the `html` tag from `src/ui/html.js` — no JSX, no compile step). Shared components live in `src/ui/`: `controls.js` (Button, IconButton, Chip, Field, GrowingTextarea, Switch, Stepper, EmptyState), `Dialog.js` (one Dialog that is a bottom sheet on phones and centered on wider screens, plus promise-based `confirmDialog()` — use it instead of `window.confirm`), `Icon.js` (the stroke icon set — use icons, not emoji, for UI controls), `AppShell.js` (signed-in frame: top nav on desktop, bottom tab bar on phones), `StageStrip.js`, `hooks.js`, `router.js`. Dialogs push a history entry so the phone's Back gesture closes the top one (see the stack at the top of `Dialog.js`); navigate with `navigate()` from `router.js`. UI rules: every control at least 44×44px on touch (`--control`), every form field 16px (iOS zooms into smaller ones), hover styles only inside `@media (hover: hover)`.

**Retro board state is centralized in one reducer.** `src/views/retro/reducer.js`'s `retroReducer` is the single point every state change flows through: the initial `GET /retros/:id` payload, every inbound WebSocket event (via `src/ws.js`'s `createRetroSocket`, wired up once in `Board.js`), and local optimistic updates (e.g. vote-before-server-confirms). Because the WS handlers are bound once on mount, routing everything through `dispatch` avoids stale-closure bugs. Entry events are upserts (`mergeEntry`) because a client's own API response and the WS echo can both arrive in either order — and in a staged retro the echo is a `hidden` placeholder that must never overwrite the author's own copy. `Board.js` owns the screen: stage-specific views (`StageViews.js`: setup, discussion, summary), lanes (one at a time with swipe on phones, a grid on desktop), the docked `Composer` on phones, `NoteActions`, `FacilitatorSheet` and `ColumnsDialog`. `RetroView.js` loads the retro and shows the join screen to first-time guests.

**Retro-end animations are a pluggable pool.** `src/views/retro/retroEndAnimations.js` exports `playRetroEndAnimation(onComplete)`, which picks a random entry (deliberately regardless of `prefers-reduced-motion`) from an array of `show*` functions (`shutdownScreen.js`, `solitaireCascade.js`, `marioEnding.js`, `deathStarEnding.js`, `pokeballEnding.js`, `bowlingStrike.js`, `shiningDoor.js`) — each a self-contained, dependency-free module that builds its own full-screen overlay (styled in `src/styles/effects.css`) and calls `onComplete` when done; `Board.js` then loads the wrap-up summary. To add a new one, write a new `show*.js` following the same shape and add it to the array; no other wiring needed.

**Styling is cascade layers + tokens.** `src/styles/layers.css` declares `@layer reset, tokens, base, components, views, effects;` and every stylesheet wraps its rules in one of those layers, so a later layer wins regardless of selector specificity — don't fight specificity or reach for `!important`, put the rule in the right layer. `tokens.css` holds the design tokens (grounds, ink, `--accent`, the four lane colors `--lane-0..3` with `-soft`/`-ink` variants, spacing `--s-1..7`, radii, `--control`); the dark palette is `:root.theme-midnight`, toggled by `applyTheme()`/`setTheme()` in `src/utils.js` (choices: system/daylight/midnight). `components.css` styles `src/ui/`; `app.css`, `board.css` and `landing.css` style the views; `effects.css` holds the vote celebration and the retro-end animations. New styles go in the matching file and layer; use tokens, not literal colors (text colors are checked to WCAG AA in both themes).

**Tests share one throwaway SQLite file for the whole run.** `vitest.config.js` sets `DB_PATH=./test/tmp/test.db` and `fileParallelism: false` specifically because test files run sequentially against the same on-disk database (wiped fresh by `test/global-setup.js` before the run) — don't parallelize test files or assume isolated state between them. `test/helpers.js` has shared fixtures (`loginAdmin` — a dedicated `testadmin` account, since the seeded admin/admin is locked out of the API until its password changes — `registerUser`, `createRetro`, etc.) — reuse them rather than re-authenticating by hand in new tests.

**UI strings are English.** All user-facing text (buttons, labels, toasts, server error messages) is in English, as are code comments and identifiers. The app was Turkish before 5.0; migration step 4 in `server/db.js` renames the untouched Turkish built-in templates, while user-created templates and retro content are left as written. Match this when adding UI.
